# WAF Microservice 개발 및 배포 계획

이 문서는 WAF Microservice 프로젝트의 개발 환경 구성과 최종 클라우드 배포 아키텍처에 대한 계획을 정리합니다.

## 1. 로컬 개발 환경

**목표**: 개발자가 자신의 PC에서 빠르고 비용 없이 독립적으로 기능을 개발하고 테스트할 수 있는 환경을 구축합니다.

- **방식**: `docker-compose`를 사용하여 프로젝트의 모든 서비스를 로컬 컨테이너 환경에서 실행합니다.
- **구성 요소**:
    - **애플리케이션**: `responder` 등 각 마이크로서비스를 Docker 컨테이너로 실행합니다.
    - **데이터베이스**: AWS ElastiCache 대신 **Redis (또는 Valkey)를 Docker 컨테이너로 실행**하여 사용합니다.
- **연결 방식**: `responder` 애플리케이션은 Docker의 내부 네트워크를 통해 `redis`라는 서비스 이름으로 데이터베이스 컨테이너에 접속합니다.
- **장점**:
    - AWS 서비스 사용 없이 완전한 기능 테스트 가능
    - 빠른 개발 및 테스트 사이클
    - 인터넷 연결 없이도 개발 가능

## 2. 최종 클라우드 배포 아키텍처 (AWS)

**목표**: EKS의 높은 비용을 피하면서, 안정적이고 확장 가능하며 비용 효율적인 아키텍처를 통해 서비스를 배포합니다.

- **핵심 전략**: **AWS ECS (Elastic Container Service) with Fargate**를 사용하여 서버리스 컨테이너 환경을 구축합니다.
- **구성 요소**:
    - **컨테이너 레지스트리**: **Amazon ECR (Elastic Container Registry)**
        - 로컬에서 빌드된 Docker 이미지를 저장하고 관리하는 중앙 저장소.
    - **로드 밸런서**: **AWS ALB (Application Load Balancer)**
        - 외부 인터넷 트래픽을 받아 실행 중인 컨테이너에 안전하게 분산.
    - **컴퓨트 (컨테이너 실행 환경)**: **AWS ECS on Fargate**
        - 서버(EC2) 관리 없이 컨테이너를 실행하는 서버리스 환경.
        - 사용한 만큼만 비용을 지불하여 비용 효율성이 매우 높음.
    - **데이터베이스**: **AWS ElastiCache (Valkey 또는 Redis)**
        - 관리형 인메모리 데이터베이스로, 운영 부담을 최소화.

### 배포 워크플로우

1.  로컬에서 개발이 완료된 애플리케이션을 Docker 이미지로 빌드한다.
2.  빌드된 이미지를 **ECR**에 Push한다.
3.  **ECS**에서 ECR 이미지를 사용하여 Fargate Task를 정의하고 Service로 실행한다.
4.  **ALB**가 외부 요청을 받아 ECS Task로 전달한다.
5.  ECS Task는 내부적으로 **ElastiCache**에 연결하여 데이터를 처리한다.

이 아키텍처는 코드 변경 없이 환경 변수 설정을 통해 로컬 환경과 운영 환경 간의 전환을 원활하게 지원합니다.
